# Deployment

How `npm run deploy:ci` (Workers Builds) and `npm run deploy` (a laptop) put the app online, and what each step refuses. The agent-facing version, with the reason for every step, is the `la-table-deploy` project skill (`.claude/skills/la-table-deploy/SKILL.md`). Back to the [README](../README.md).

The static demo is a second Worker, `la-table-demo`, assets only, deployed by `npm run deploy:demo` (`scripts/deploy-demo.ts`, then `npm run build:demo`, then `wrangler deploy --config wrangler.demo.jsonc --env-file=/dev/null`) from its own Workers Builds entry and nothing else: deploy command exactly `npm run deploy:demo`, production branch `main`, non-production branch builds off and their deploy command set to exactly `npm run deploy:demo` too (the default non-production command, the Preview command, `npx wrangler preview` per Cloudflare's Workers Builds documentation on 2026-11-15, `npx wrangler versions upload` on older entries, has no `--config`: it never runs the gate and reads `wrangler.jsonc`, so it would upload the app's code, D1 binding and variables as a version of `la-table-demo`; the gate refuses every branch but `main`, so the toggle left on fails closed), watch paths: the ones `node scripts/demo-watch-paths.ts` prints (`DEMO_WATCH_PATHS`, never listed in a doc; `scripts/demo-watch-paths.test.ts` fails when the demo build, its Vite configuration or `scripts/deploy-demo.ts` reads a file outside them). `wrangler.demo.jsonc` carries no `main`, binding, variable or route (`scripts/deploy-demo.ts` refuses them at deploy time, before the build, in the file as wrangler parses it and in wrangler's normalised reading of it, a `"__proto__"` key included, and refuses too outside Workers Builds, on a branch other than `main`, and when `WRANGLER_CI_OVERRIDE_NAME` names another Worker than `la-table-demo`, which would otherwise publish the demo over that Worker, and when no dotenv file (`.env`, `.env.local`, any `.env.*` but `.env.example`) sits at the repository root (wrangler loads `.env` and `.env.local` into its environment on every command, after the gate read it, so `WRANGLER_CI_OVERRIDE_NAME=la-table` there would retarget the upload; `deploy:demo` also runs wrangler with `--env-file=/dev/null`, so it loads none)), and it has no Access, so only invented data may ever be in it. Once the entry exists, both its deploy commands, production and non-production, read `npm run deploy:demo`. The rest of this page is the app's gate, `deploy:ci`.

Deployed at the Worker's own address, `https://la-table.william-445.workers.dev`, on the Cloudflare Workers free tier, behind a Cloudflare Access policy on the Worker that admits the two owners' email addresses (one-time PIN) and two service tokens: the planning CLI's, kept in the keychain, and the build's own, kept only in Workers Builds' encrypted build secrets. Workers Builds installs the dependencies and runs `npm run deploy:ci` alone (no build command) on every push to `main` (any other branch it names is refused): a configuration check; then, with wrangler's own credential, Cloudflare's API asked for the account's workers.dev subdomain (the address must be on it, or Access would be checked on another account's Worker) and for any route or custom domain attached to the Worker in the dashboard (refused: the app has its workers.dev address only), and the Worker's secrets listed (any refused: the Worker holds none, and a secret survives every deploy); a live check that Access answers the address and takes the build's token (a refused token stops the build before it builds anything) (on the page, the API, and two paths drawn at random each run, so Access scoped to a few paths does not pass), the D1 restore point, the pending migrations (then a check that wrangler lists none left), the same Access check again, and the Worker's routes, domains and secrets read again, seconds before the upload (the build and the migrations take minutes), the deploy, tagged with the commit (wrangler must name the app's own workers.dev address, a second look at the subdomain in the address belonging to the account in the configuration), then a check that this commit's version answers on the address through Access (the build reads its own service token, `la-table-build`, from its build secrets for that). `deploy:ci` runs the typecheck, the tests and the build itself, on the commit it deploys, so a red suite never deploys, whatever the working tree held. `npm run deploy` does the same from a laptop, for a clean tree at `main` as GitHub holds it only (fetched from the GitHub URL itself, never through `origin`, so neither a stale local copy of main nor an `origin` pointing elsewhere can pass). The Workers Builds mode is declared by its variables (`WORKERS_CI=1`, `WORKERS_CI_COMMIT_SHA`, `WORKERS_CI_BRANCH`), which nothing checks against GitHub: never set them in a shell. The deploy script itself, every module it imports, `package.json` and `tsconfig.json` run from the working tree, so they must also be the commit's, byte for byte, and no `node_modules` may sit beside them below the repository's own, where Node would find another `wrangler` first. Either way the checked commit is exported to a fresh directory under the system's `/tmp` (never where the shell's `TMPDIR` points), refused when a directory above it holds a TypeScript or package configuration or a `node_modules`, which the build would read, proved equal to the commit file by file, given the repository's `node_modules` only when its installed lockfile matches the commit's `package-lock.json` (otherwise run `npm ci` first), and built and deployed from there, never from the working tree (whose changes git can be told to hide from `git status`), with git reading every object as stored (a local `git replace` of main by another commit is ignored); wrangler runs from an environment built from nothing, with the Worker, the account, the configuration and the assets named on its command line: no shell variable, `.env` file or stray configuration can send the deploy elsewhere, and neither the Worker nor the app is compiled with a TypeScript configuration, nor built by an npm reading a configuration file (`$HOME/.npmrc` or the global one), from outside the repository (`wrangler.jsonc` names the Worker's, and the root `tsconfig.json` ends the search for one). A proxy or TLS variable set for the deploy itself (`HTTPS_PROXY`, `NODE_USE_ENV_PROXY`, `NODE_TLS_REJECT_UNAUTHORIZED`, `NODE_EXTRA_CA_CERTS`, `NODE_USE_SYSTEM_CA`, `SSL_CERT_FILE` and the like) stops it before anything runs, since the Access check would go through it, and so does a process that trusts any certificate authority beyond those built into Node, whatever added it. A `TSX_` or `ESBUILD_` variable, a `NODE_OPTIONS` setting other than memory or warnings, or a run from outside the repository stop it too, since each says the deploy itself would load other code. These checks catch a misconfigured environment, not a hostile one: they run once the deploy's own code has loaded, so the environment and the files that launch the deploy are trusted, as the installed `node_modules` is.
