# The deploy gate

Two Workers, one deploy path each. `la-table`, the app, deploys through `npm run deploy:ci` only, described below. `la-table-demo`, the static demo (assets only, no code, no binding, no variable, no Access), deploys through `npm run deploy:demo` (`scripts/deploy-demo.ts`, then `build:demo`, then `wrangler deploy --config wrangler.demo.jsonc --env-file=/dev/null`) from its own Workers Builds entry only: deploy command exactly `npm run deploy:demo`, production branch `main`, non-production branch builds off and their deploy command set to exactly `npm run deploy:demo` too (the default non-production command, the Preview command, `npx wrangler preview` per Cloudflare's Workers Builds documentation on 2026-11-15, `npx wrangler versions upload` on older entries, has no `--config`: it never runs the gate and reads `wrangler.jsonc`, so it would upload the app's code, D1 binding and variables as a version of `la-table-demo`; the gate refuses every branch but `main`, so the toggle left on fails closed), watch paths as `docs/deploy.md` lists them. `scripts/deploy-demo.ts` is the demo's gate and runs first: it exits 1 before the build unless `WORKERS_CI=1` on `main`, `WRANGLER_CI_OVERRIDE_NAME` is unset or `la-table-demo`, no dotenv file (`.env`, `.env.local`, any `.env.*` but `.env.example`) sits at the repository root (wrangler loads `.env` and `.env.local` into its environment on every command, after the gate read it, so `WRANGLER_CI_OVERRIDE_NAME=la-table` there would retarget the upload; `deploy:demo` also runs wrangler with `--env-file=/dev/null`, so it loads none), and `wrangler.demo.jsonc` passes its allowlist of keys, the name `la-table-demo` and the app's account. The gate reads both configurations with wrangler's own raw reader (`experimental_readRawConfig`, the read and JSONC parse `wrangler deploy --config` runs), never a parser of its own: one that ended a `//` comment only at `\n`, where wrangler also ends it at a lone `\r`, let a D1 binding past the allowlist and into the upload; re-check that export when wrangler is upgraded. That reader makes a `"__proto__"` key the parsed object's prototype: `Object.keys` skips it, a property read and wrangler's normalisation follow it, so a `main` and a D1 binding written there passed an allowlist of own keys. The gate reads own properties only, refuses any parsed object or array that is not a plain one (`nonPlainPaths`), and also compares wrangler's normalised reading (`unstable_readConfig`, `env: ""`) of the file, key by key, with that of the one allowed configuration (`normalisedConfigProblems`), refusing any difference and any non-plain value there too (`isDeepStrictEqual` ignores an inherited property). wrangler 4.157.0 deploys under `WRANGLER_CI_OVERRIDE_NAME` whatever `--config` or `--name` says (`mergeSharedConfigArgs`), so the demo command pasted into the app's entry would publish the static demo over `la-table`, its D1 binding, variables and code dropped; re-check that when wrangler is upgraded. Never run plain `wrangler deploy` in a demo build: Workers Builds names the target through `WRANGLER_CI_OVERRIDE_NAME`, and without `--config wrangler.demo.jsonc` that would publish the app's Worker, D1 binding included, under the demo's name. The rest of this file is the app's gate. This skill holds the mechanism behind the rules a project's own instructions state. The code's doc comments (`scripts/deploy-ci.ts`, `scripts/deploy-target.ts`, `scripts/deploy-config.ts`) are the source of truth when this text and the code disagree.

- **The app's one deploy path, `scripts/deploy-ci.ts`:** `scripts/deploy-config.ts` refuses a configuration that could answer on another address (`workers_dev` not true, `preview_urls` not false, a `route` or any `routes`, another Worker name, `DEFAULT_URL` not the Worker's workers.dev address), deploy to an unnamed account, carry the local bypass, bind a placeholder, or bind a second D1 database (wrangler resolves `la-table` to the first entry named so, for the bookmark and the migrations); the deploy then exports the checked commit to a fresh directory under the system's `/tmp` (`exportCommit`; `WORKSPACE_PARENT`, never `os.tmpdir()`, which reads the caller's `TMPDIR`), refuses it (exit 1) when a directory above it holds what the build reads from there (`ANCESTOR_REFUSED`), proves the export equal to it file by file, raw hashes against its blobs (a local filter or attribute rewrites `git archive`: refused), proves the deploy's own running files equal to the commit's the same way (`gateFiles`: `scripts/deploy-ci.ts`, every module it imports, `GATE_EXTRA`, and every file `tsconfig.json` extends, whose `paths` tsx honours too (`extendedConfigs`; an `extends` outside the repository exits 2); they run from the working tree, so an edit git status does not show exits 1), refuses (exit 1) a `node_modules` in any directory between those files and the root (`shadowingModules`: Node would resolve `wrangler`, the configuration reader and the binary, there before the repository's own, and `node_modules/` is gitignored at any depth), and a probed address other than the commit's `DEFAULT_URL` (exit 2 when the commit's `src/cli/client.ts` declares none), links the repository's `node_modules` into it only when `node_modules/.package-lock.json` matches the commit's `package-lock.json` (`installMismatch`: another branch's install left in place would bundle, build and deploy other dependencies under this commit's tag; exit 1, run `npm ci`), gates the export's own `wrangler.jsonc` again, derives its target once from the export (Worker, account, address, configuration, assets, the checked commit) and prints it; reads wrangler's own credential (`wrangler auth token --json`, a pinned step: Workers Builds' API token, or the laptop's OAuth login; never logged, never handed to a subprocess) and with it the account's workers.dev subdomain from Cloudflare's API (`/accounts/<account_id>/workers/subdomain`): `DEFAULT_URL` on another subdomain exits 1, before Access is asked (the probe would otherwise see another account's Worker and Access while the deploy goes to this account's address), an unreadable credential or API answer exits 2; lists, with the same credential, the routes of the Worker's default environment and its custom domains (`attachedHosts`: a route or a domain attached in the dashboard is outside `wrangler.jsonc`, which the configuration gate reads) and refuses any (exit 1; unreadable, exit 2, a custom domain entry with no readable `service` included: it is never dropped, it could be this Worker's); lists the Worker's secrets (`wrangler secret list`, a pinned step) and refuses any (exit 1; an unreadable list exits 2): a secret survives every deploy, `keep_vars` spares plain variables only, and the Worker holds none, so a `DEV_SKIP_ACCESS` put as a secret is caught there (the Worker also honours it only on localhost, `isLocalRequest`: workerd gives no other local-only signal, since miniflare mocks `request.cf` and sets `CF-Connecting-IP` only when the request lacks one); a live probe must see Access answer the address (a 302 to the team's login on `/`, `/api/health`, and a path under `/api/` and one at the root drawn fresh each run, so Access scoped to named paths only is refused) or nothing deploys; the service token is then tried once on `/api/health` (`tokenAccepted`: a redirect to the login, a 401 or a 403 is a refusal, exit 2 « jeton Access refusé »; any other answer, the placeholder's 503 included, means Access let it through), after the subdomain proof so that it goes only to the account's own address, and before the build, so a token missing from the `CLI` policy or pasted swapped fails before anything is written; then `npm run build:ci` runs in the export (the commit's own typecheck and tests, never the working tree's, then `dist/`; red, nothing deploys), the D1 Time Travel bookmark is printed (the restore point before migrations; no bookmark in wrangler's answer, no migration), `wrangler d1 migrations apply --remote` runs, `wrangler d1 migrations list --remote` must then print `NO_PENDING_MIGRATIONS` (apply can exit 0 with a migration unapplied), Access is asked again the same way, then the routes, domains and secrets are read again (`workerRefusal`, the same refusals; the build and the migrations take minutes, in which the dashboard can add any of them; refused, nothing is uploaded), and `wrangler deploy --tag <commit[:12]>`, whose printed workers.dev address must be the target's (`deployedAddresses`: the second look, after the upload, at `DEFAULT_URL`'s subdomain being `account_id`'s; another address exits 1 at once, none read exits 2); last, `/api/health` asked through Access with the service token, in rounds, must name that tag, with Access still answering a visitor without a session, or the deploy exits 1 (another version, Access gone) or 2 (never reached). Never `wrangler deploy` the app by hand, and never run a deploy step in the working tree: git can hide its changes from `git status` (skip-worktree, assume-unchanged, `info/exclude`, `status.showUntrackedFiles`, a `git replace` of main), so the clean-tree check is a courtesy, the export is the guarantee. Git runs with replace refs off (`GIT_NO_REPLACE_OBJECTS` in `baseEnv`), or a local `git replace` of main makes every git read of it, the export and its proof included, return another commit.
- **Wrangler runs only through `pinnedWrangler` (`scripts/deploy-target.ts`)**, the deploy's steps and the restore drill's local ones (`DrillStep`: `d1 execute --local` on `DRILL_DIR`) alike, every step built from the target alone (`--config`, `--env=`, `--env-file=/dev/null`; `--name` and `--assets` for the deploy), in an environment built from nothing (`baseEnv`, the target's account, Workers Builds' API token), and git and the build run in `baseEnv` too; the build's npm also gets `BUILD_ENV_PINS` (`buildCall`): `NPM_CONFIG_PINS`, so it reads no `$HOME/.npmrc` and no `etc/npmrc` beside Node, outside the commit, where a `node-options` or a `script-shell` decides the build's verdict (a build step never reads a configuration file from outside the commit), and `NO_COLOR`, since `baseEnv`'s `CI=1` turns colour on in vite's picocolors and vitest's tinyrainbow and the log would carry escape codes between the words a reader looks for. git, tar, find and ln run by absolute path from `/usr/bin` or `/bin` (`systemTools`; neither holds one, exit 2), and the keychain's `security` as `/usr/bin/security` (`SECURITY_BIN`), never through PATH, which starts with Node's directory, where `npm i -g` puts every global bin. Never add a wrangler step, a flag or a variable any other way: wrangler also takes its target from ambient variables and stray files (`CLOUDFLARE_ENV`, `WRANGLER_CI_OVERRIDE_NAME`, `CLOUDFLARE_ACCOUNT_ID`, `.env`, another config, a `.wrangler/deploy/config.json` redirect, its account cache), and a gate that checks one input while wrangler reads another deploys somewhere unchecked. `WRANGLER_DROPPED` lists what is dropped and why: re-check it against `wrangler-dist/cli.js` when wrangler is upgraded. **No build reads a tsconfig.json from outside the repository:** esbuild and Vite otherwise look in every directory above the sources, an export's parents included, where one can remap `jose` in the Worker or recompile the app. `wrangler.jsonc` names `tsconfig` (the gate refuses it unnamed) and the root `tsconfig.json` stops Vite; it must include every file and set only the base options, since `scripts/build-isolation.test.ts` pins both builds byte-identical under a hostile parent. The Access probe runs in the deploy's own process, so `deploy:ci` refuses to run (exit 2) when a variable that would route or loosen its fetch is set (`PROBE_ENV_REFUSED`: a proxy, `NODE_USE_ENV_PROXY`, `NODE_TLS_REJECT_UNAUTHORIZED`, a variable that adds certificate authorities), and when the process trusts any authority beyond those built into Node, whatever added it (`widenedTrust`), and when its own settings say it would load or resolve other code than the commit's (`processRefusal`: a `TSX_` or `ESBUILD_` variable, a `NODE_OPTIONS` token outside `NODE_OPTIONS_ALLOWED`, a working directory other than the repository, whose `tsconfig.json` tsx would not read). These process checks catch an honest misconfiguration of the deploy's own environment, never a hostile one: they run once every module has loaded, so code an option already loaded can hide from them. The environment and the user's files that launch `deploy:ci` are trusted, as the contents of `node_modules` are; the gate's guarantees are about the commit, its export and what the subprocesses read. `deploy-ci.property.test.ts` runs the path under random hostile variables and stray files, and on trees whose changes git hides; `deploy-ci.test.ts` sets each dropped name in turn (`HOME` and `PATH` included), then all of them at once, in both modes and in its own process environment too, with the expected `baseEnv` read before, so a single leak never depends on a draw. Wrangler is a stub there: `deploy-target.test.ts` runs `wranglerPins` through the installed wrangler (local D1 only), the one test that sees what the flags mean to it.
