# Planning a batch of meals

Spec: `docs/spec.md` §5 (rules), §7 (protocol). Thresholds: `src/domain/rules.config.ts` — read them there, never restate them.

The CLI is the only way to read or write: `npm run plan -- <command>` (add `--local` against `wrangler dev`). Exit `0` clean · `1` blocks or refused (final) · `2` could not run, or « réponse non définitive » (the server recorded nothing it can stand behind). **On exit 2, stop and report the message; never continue on a guess of the state** (except the reruns that steps 2, 3 and 9 allow).

## Steps

1. **Back up.** `npm run backup`. Exit 2 → stop: no planning without a backup.
2. **Read the state, then settle the receipts first.** `npm run plan -- status`; read it all, but act on the receipts before anything else (calibration reads only fully priced trips, spec §5.5), and before « Restes à préciser »: a `reste` answer opens the item, and `bought` then refuses it (« reste déclaré depuis, à préciser avec reste »). For each trip without a total, ask the owner for the receipt total → `npm run plan -- total <trip> <euros>` (a trip recorded without a receipt is not listed: it needs neither a total nor prices on its lines, and `total` on one is refused « passage sans ticket »); for each line to price, propose an estimate and confirm → `npm run plan -- price <line> <euros>`, but a loose line (sold by weight or count) gets its quantity first with `bought` below, since a price typed is for the line's quantity as it then is. Both set a value, so after « réponse non définitive » (exit 2) re-run the same command once; any other exit 2 → stop. **Receipt photo:** read every line; propose the reference prices that changed and the pack formats it prints (« RICOTTA 250G », « C.FR EP 15 » = 15 cl), match each to a catalogue name, show the owner only doubtful matches, then `npm run plan -- packs <scratchpad>/packs.json` on the go. An entry needs `pack`, `price` or both: omit a field to keep it as it is, `null` clears it, so a receipt that prints no format is a price-only entry. The output prints each field the entry sends that changed, before → after (« ~ comté : prix 4,20 € / 250 g → 4,35 € / 250 g », « = » unchanged); a pack and a price that would end in two units are refused (« le paquet et le prix doivent être dans la même unité »). Then, for each loose line on it (sold by weight or count, not in packs), read the weight or count bought and send `npm run plan -- bought <line> <mots…>` (« 1,2 kg », « 4 » for pièces; the words parse in the line's unit; over 10 times the line's planned quantity, or under a tenth of it, it asks for `--oui`, which you add only when the receipt says so). It prints the line and its Reste item before → after (« ~ chou blanc : 250 g → 1,2 kg · Reste #46 250 g → 1,2 kg »), and any meal a lower quantity left short, which then shows under « Manques ». A receipt at or below what was already eaten prints « → quantité inconnue »: `bought` cannot set that item again, so ask the owner what is left and answer it under « Restes à préciser » (`plan -- reste`). It sets a value, so after exit 2 re-run it once. Calibration may rise after loose receipts: the extra weight was really paid for, so it is real spend; never correct it by hand.
3. **Then the rest of `status`**, re-read once the receipts are in, starting with « Restes à préciser » (open items whose quantity is unknown or 0): ask the owner what is left of each and record only their words with `npm run plan -- reste <id> <mots…> [--low|--pas-low]` (the phone's own `stock.partial`: the server parses the words into the item's unit; « presque fini » stays as it is unless a flag says; a set value, so after exit 2 re-run it once); never guess a quantity. What the owner says is gone (« plus de lait », « il n'y en a plus ») is `npm run plan -- fini <id>…`, never `reste <id> 0`: a zero in words is read as unknown, and an unknown staple still counts as at home. An item a meal holds is refused there: the owner finishes it on the phone, choosing « racheter » or « retirer le repas ». Then « Manques »: open meals left short, by a declared leftover (what the owners said is left is below what the meals held, so the latest planned lost their hold) or by a planned line the owners took off Courses « On n'en prend pas » (the meal keeps needing it), one line per meal and product (« comté : 60 g manquent pour … (#12) »). `planning.commit` lines serve its own new meals only, so show each « Manque » to the owner with its free stock (« (Reste : 950 g libres) » when some exists), or as a reason to drop or swap that meal; on the owner's go, `npm run plan -- manques [<repas>…]` covers them (free Reste stock first, then Courses; it prints where each amount went; after exit 2 re-run it, a covered meal answers « rien ne manque »). Then: pool, Reste by urgency, envies, feedback since the last planning, calibration.
4. **Ask the session parameters:** how many meals to add (default 7; the pool carries over — "7 more" or "only 2"), portions (default 2, per-meal overrides), constraints (absences, guests, appetite for a long dish, red meat explicitly requested or not).
5. **Build candidates**, in this order: open envies → Reste items that must be used (urgent, then libre perishables) → eligible favourites → new recipes from knowledge or the web. Favour season (product calendars in the state), price, ≤ the quick-meal active time on most meals, variety against recent plannings and the feedback (« Pas pour nous » never comes back; « À refaire » makes a favourite). Web recipes keep `source_url`; rewrite the steps in French, scaled, in g / ml / pièces, as « Writing the steps » says.
6. **Write `proposal.json`** in the session scratchpad (never in the repo), in the §7.3 format. `prices` is only needed for lines whose product has no reference price in that unit (`check` names a proposal price it ignored for differing from the reference); a price in `prices` is for the whole line, rounded up to the pack: `check`'s « prix manquant » names that quantity and the pack (« ricotta (250 g, paquet de 250 g) »). New products need a category and roles from `src/domain/vocabulary.ts`, season months when fresh produce, shelf lives when perishable. A new spice gets the role `assaisonnement` (recipe nutrition ignores it); salt does not.
7. **Check.** `npm run plan -- check <scratchpad>/proposal.json`. Fix every `✗` block yourself and re-run until none remain. Keep the `!` warnings for the owner.
8. **Present**, one line per meal: title, why (season / uses X before date / envie / favourite), € per portion, active time, « à cuisiner tôt » when flagged; under it, the meal's nutrition line from `check` (`≈ … kcal/portion · … g protéines`, « (partiel) » when an ingredient has no values); then the totals against budget (raw and calibrated) and the warnings. Show `pack-leftover` warnings: propose a meal that finishes the pack, or accept the leftover. For a few trips after packs land, calibration runs high (older trips were estimated at the exact need), so a `budget` warning then may be spurious. The owner swaps, drops, asks for alternatives: edit the file and re-run `check` after every change.
9. **Ask which staples are already home; write them to Reste** with `npm run plan -- stock` (see « Stocking Reste from a dictation »), then re-run `check`, which drops their staple lines. **Commit only on the owner's explicit go** ("ok", "go", "on valide"): `npm run plan -- commit <scratchpad>/proposal.json`. It re-checks against a fresh state, records its op id in `<scratchpad>/proposal.json.envois.json`, sends, clears that entry once the server's answer is final, and prints Courses by category.
   - **Exit 2 during commit** (network, Access, « réponse non définitive »): the planning may or may not have landed. Re-run **the same command on the unchanged file**, in this session: it resends the same op id: the server replays what it recorded, or evaluates it again if it recorded nothing; a second exit 2 → stop and report. Never edit `proposal.json` before that rerun — an edited file is a new proposal and can become a second planning.
   - If that rerun reports « journal … illisible », stop and report: do not edit or delete the journal.
   - The journal belongs to this session's scratchpad. An entry an exit 2 left behind, for a proposal then abandoned or edited, stays in it and does no harm: resent later, that id is replayed or evaluated again. It goes with the scratchpad; never prune it by hand mid-session.
   - **Exit 1**: the server refused and recorded it, so it is final. Show the reason; the state moved (a phone ticked, a meal was dropped): re-run `status`, adjust the proposal, `check`, and ask for the go again.
   - **After a commit that created products**, give them nutrition values: add a line per new product to `data/nutrition-map.json` (quantities and `grams_per_piece` are as bought, bone, shell and peel included: set `edible_pct`, the eaten share of the bought weight, moules 30, poireau 60, cuisse de poulet 75, banane 65, default 100; it applies to g and piece quantities, not ml; a canned Ciqual entry « égoutté » is a drained value while recipes use the net weight, so set the drained share), run `npm run --silent ciqual > <scratchpad>/nutrition.json` (`--silent`, or npm's banner lands in the file), then `npm run plan -- nutrition <scratchpad>/nutrition.json`. Until then they count nowhere, and `status` lists them under « Produits sans valeurs nutritionnelles ».
   - **Matching to Ciqual**, show the owner only what needs a decision: each uncertain match (several Ciqual candidates, or none raw — only a cooked or prepared entry), and every piece or ml weight you set. Collapse the confident matches into one line naming them.

## Never

- Commit without a clean `check`, or without the owner's go (the unchanged rerun after an exit 2 is the one exception, and it needs no new go).
- Write to D1 any other way (no `wrangler d1 execute`, no raw SQL).
- Touch anything the phones own: ticks, Reste items, cooked meals. The exceptions are `stock` below, `reste` (step 3) and `bought` (step 2, on the receipt only), and only for what the owner dictates, answers or the receipt prints.
- Keep a proposal, its `.envois.json` journal, a backup or a secret in the repo.

## Writing the steps

The owners asked for steps that teach the gestures that make the dish better, not a bare sequence. Each step says what to do, how, and the sign that it is done; the technique that changes the result goes in the step where it happens, with its reason in a few words (« pour qu'il dore au lieu de bouillir »). Read on a phone at the stove: one action per step, at most three short sentences, the heat named (« feu moyen-vif »), a time **and** a sensory cue (« 8 min, jusqu'à ce que les oignons soient translucides »).

- **Mise en place** first when timing is tight (a stir-fry, a sauce): cut and measure everything before the pan heats. Name what can be done ahead, or during another step's wait.
- **Spices:** toast whole spices dry in the pan, 1 to 2 min, until they smell, before grinding or adding; bloom ground spices in the hot fat 30 s before the liquid, never in boiling water.
- **Fish, meat, tofu to sear:** out of the fridge 15–30 min before (meat), pat dry with paper towel, salt shortly before (or 40 min ahead for a thick piece), a hot pan, not crowded, not moved until it releases; fish skin side down, pressed for the first seconds. Never rinse poultry. Rest meat a few minutes before cutting.
- **Aromatics:** onion before garlic, garlic only until it smells (it burns and turns bitter); a pinch of salt on onions to sweat them.
- **Vegetables to roast:** dry, spread out in one layer, high oven (200–220 °C), turned once.
- **Pasta, grains:** pasta water salted like the sea, keep a ladle of it for the sauce; toast rice or bulgur in the fat before the liquid; rinse rice that must stay separate, not risotto rice.
- **Pan sauces:** deglaze the browned bits with the liquid; finish with a knob of butter off the heat.
- **The end:** taste and adjust the salt; an acid (lemon, vinegar) or fresh herbs at the last minute when the dish is rich or flat.

Only what this dish needs: two or three of these gestures per recipe, never the whole list, and no filler (« bon appétit », « selon votre goût » without a measure). Recipes already committed keep their steps: no op rewrites them.

## Stocking Reste from a dictation

When the owner lists what is already at home (the first stock, or a cupboard found again), write it with `npm run plan -- stock <scratchpad>/inventaire.json`, never as a planning. The file: `{ "items": [ { "product": "huile d'olive", "qty": "1,5 bouteille", "low": false, "useBy": null } ] }`. `product` is a catalogue name (`null` for free text, then `label` is required; `label` otherwise defaults to the product name); `qty` is the owner's words; `low: true` for « un peu », « un fond »; `useBy` only when the owner gives one (otherwise the product's shelf life sets it).

- Map each dictated thing to the catalogue name first, whatever the owner's spelling (« zaatar » is `za'atar`, « cumin moulu » is `cumin` with that label): a near-duplicate product splits recipes from what Reste holds. The name match ignores case, spaces and ’ against ', nothing else.
- A thing the catalogue lacks is a catalogue product first: `npm run plan -- catalogue <scratchpad>/produits.json`, before the stock is written. The file is `{ "products": [ … ] }`, each in the `new_products` shape (§7.3); it adds the unknown ones, updates the ones whose fields differ (`~` names the fields) and leaves the rest (`=`). An update the meals in progress depend on (a staple flag the coverage counts on) is refused: redo it after that planning. Free text is for what no recipe will ever ask for.
- `qty` words that parse in the product's unit (« 500 g », « 1,5 kg », « 20 cl », « 2 boîtes » when it has a pack) become its quantity; anything else, a bare number on a product in grams, or a free-text item keeps the words with the quantity unknown. An « Il en reste » recorded for the owner is the phone's own `stock.partial`, so it is a write like theirs: the phone's undo of a cook that touched that item then reads « modifié depuis », and an undo of an « Il en reste » whose raised quantity a planning has reserved since is refused « réservé depuis pour un autre repas ».
- The whole file is refused (exit 1, nothing sent) on any wrong line. A label already unfinished in Reste is skipped, so after an exit 2 the same command finishes the run without a duplicate. « Bientôt fini » is set only on rows the run added; a skipped row with `low` is named in the output, for the phone.

## First time on a machine

The CLI reads the Access service token from the macOS keychain:

```bash
security add-generic-password -U -s la-table-access-client-id -a "$USER" -w
security add-generic-password -U -s la-table-access-client-secret -a "$USER" -w
```

Each asks for the value at a prompt (twice): paste the Client ID, then the Client Secret, from the service token `la-table-cli`. Nothing goes on the command line, so nothing reaches the shell history. The build has its own token, `la-table-build`, kept only in Workers Builds' build secrets: never put one token in the other's place.

Off macOS there is no keychain: set `LA_TABLE_CLI_ACCESS_CLIENT_ID` and `LA_TABLE_CLI_ACCESS_CLIENT_SECRET` to the same two values instead (the CLI's own names, never the build's `LA_TABLE_ACCESS_CLIENT_*`, which are another token's: set alone they exit 2 naming the CLI's). On macOS the environment is read only when the keychain read yields neither entry (absent, locked, or a non-GUI session such as ssh or a LaunchAgent), and the keychain wins when both hold a token. Only one of the pair set is exit 2. The probes stay keychain-only.

A missing entry is exit 2 naming it. The token goes only to `DEFAULT_URL` (a loopback `LA_TABLE_URL` gets no token and no keychain read), never to the provisional `replace-me` subdomain (which any account can claim, spelled with a root dot or not): until the deploy setup fills `DEFAULT_URL`, a remote command exits 2 before reading the keychain, and so does an `LA_TABLE_URL` that is anything else (the environment is not read before that check either). The token is created with the Access application.
